# CAN 应用层协议

## 1. 物理层和帧格式

- 使用经典 CAN 2.0A，标准数据帧，11 位标识符。
- 两节点波特率均为 250 kbit/s。
- 当前电机控制只接受**标准帧、数据帧、ID=0x301**；扩展帧和远程帧不会进入电机控制分支。
- 经典 CAN 的 DLC 范围是 0~8，表示数据字节数。合法 `0x301` 帧要求 `DLC=8`。

F407 的 CAN1 过滤器在 `Int_can.c` 中配置为掩码全 0，也就是硬件接收所有标准帧和扩展帧；真正的 ID 分发在软件回调里完成。这样做的原因是当前工程还要兼容调试/旧协议帧，但电机控制只处理 `0x301`。

## 2. 0x301 电机控制帧

### 2.1 帧头

| 字段 | 值 |
|---|---|
| 帧类型 | 标准数据帧 |
| ID | `0x301` |
| DLC | `8` |

### 2.2 数据字节

| 字节 | 名称 | 取值 | 说明 |
|---|---|---|---|
| `Data[0]` | 帧标记 | `0xA5` | 固定值，用于快速识别电机控制帧 |
| `Data[1]` | 命令 | `0x01` 或 `0x02` | `0x01`=SET 设置速度；`0x02`=STOP 停止 |
| `Data[2]` | 速度高字节 | `0x00~0xFF` | 有符号 16 位速度的高 8 位 |
| `Data[3]` | 速度低字节 | `0x00~0xFF` | 有符号 16 位速度的低 8 位 |
| `Data[4]` | 序号 | `0x00~0xFF` | F103 每发送一帧递增；F407 当前只接收，不使用该字段 |
| `Data[5..7]` | 保留 | `0x00` | 当前 F103 填 0，F407 不解析 |

注意：速度采用**大端**存放，也就是高字节在前。F407 的解析代码是：

```c
speed = (int16_t)(((uint16_t)data[2] << 8) | data[3]);
```

## 3. 速度编码

速度字段是 `int16_t`，有效范围 `-1000 ~ 1000`：

- `0`：目标停止。
- `1 ~ 1000`：一个方向，数值映射为目标 RPM，再由 PI 产生 PWM。
- `-1 ~ -1000`：反方向，绝对值映射为目标 RPM，再由 PI 产生 PWM。

当前 `0 ~ 1000` 是 CAN 指令量纲，不是直接写入 PWM 的占空比。F407 先把它换算成目标 RPM：

```c
target_rpm = ((float)can_speed / 1000.0f) * MOTOR_MAX_RPM;
```

当前 `MOTOR_MAX_RPM = 169.0f`，所以 `+100` 对应 `+16.9 RPM`，`+200` 对应 `+33.8 RPM`。PI 的输出才是 PWM 指令，`Int_Motor_SetSpeed()` 最终把它写成 TIM3_CH3 的比较值；`ARR=999` 时：

- `CCR=0`：0% 占空比；
- `CCR=500`：约 50%；
- `CCR=1000`：100%。

### 3.1 编码示例

| 目标值 | 十进制/十六进制 | `Data[2]` | `Data[3]` | 完整数据（Data[0..7]） |
|---|---|---|---|---|
| 300 | `0x012C` | `0x01` | `0x2C` | `A5 01 01 2C 00 00 00 00` |
| -300 | `0xFED4` | `0xFE` | `0xD4` | `A5 01 FE D4 00 00 00 00` |
| 1000 | `0x03E8` | `0x03` | `0xE8` | `A5 01 03 E8 00 00 00 00` |
| -1000 | `0xFC18` | `0xFC` | `0x18` | `A5 01 FC 18 00 00 00 00` |
| STOP | — | `0x00` | `0x00` | `A5 02 00 00 00 00 00 00` |

示例中的 `Data[4]` 写成 0 只是便于阅读；F103 实际发送时会把内部 `tx_seq` 放到 `Data[4]`，F407 不使用该值。

## 4. SET 和 STOP

### 4.1 SET

`Data[1]=0x01` 时，F407 继续校验速度范围。速度合法则：

- 更新 CAN 目标值；
- 更新最后接收时刻 `last_rx_tick`；
- 清除所有 CAN 相关故障位。

### 4.2 STOP

`Data[1]=0x02` 时，F407 **不解析速度字节**，直接：

- 把 CAN 目标值设为 0；
- 更新最后接收时刻；
- 清除所有 CAN 相关故障位。

STOP 不是硬件急停。当前闭环任务在下一个 50 ms 控制周期把目标 RPM 设为 0，清除积分项并调用 `Int_Motor_Stop()`，PWM 立即归零；电机机械停止时间仍取决于负载和惯性。软件停止延迟最多约一个控制周期，不要写成“机械立即抱死”。

## 5. 校验顺序和故障位

### 5.1 校验顺序

F407 在 `App_MotorCan_OnRx()` 中按以下顺序检查，任一失败立即 `return`：

1. ID 是否为 `0x301`；
2. 数据指针是否为空、`len` 是否等于 8；
3. `Data[0]` 是否等于 `0xA5`；
4. `Data[1]` 是否为 `0x01` 或 `0x02`；
5. 对 SET 帧，速度是否在 `-1000 ~ 1000`。

### 5.2 故障位

故障位定义在 `App_Fault.h`，按位叠加：

| 宏 | 值 | 触发条件 |
|---|---|---|
| `FAULT_NONE` | `0x00` | 无故障 |
| `FAULT_CAN_TIMEOUT` | `0x01` | 超过 500 ms 没有合法 `0x301` 帧 |
| `FAULT_CAN_BAD_FRAME` | `0x02` | `len != 8` 或 `Data[0] != 0xA5` |
| `FAULT_CAN_BAD_COMMAND` | `0x04` | `Data[1]` 不是 `0x01/0x02` |
| `FAULT_CAN_BAD_SPEED` | `0x08` | SET 帧速度超出 `-1000 ~ 1000` |

故障位可以同时存在。例如帧长错误后如果一直没有合法帧，500 ms 后会出现：

```text
0x02 | 0x01 = 0x03
```

因此测试时不要只比较“是否等于 0x02”，而应检查对应位是否存在；更稳定的做法是在注入非法帧期间周期性穿插一帧合法 STOP，让 `TIMEOUT` 被清掉后再观察单一故障位。

### 5.3 非法帧对 CAN 目标值的影响

非法帧不会更新 `target_speed`，也不会更新 `last_rx_tick`，因此：

- 当前 CAN 目标值不会被非法数据直接改写；
- 如果之后一直没有合法帧，500 ms 超时会把目标值归零；
- 在超时发生前，电机仍会按上一条合法目标运行，这是当前实现的边界，不应描述成“收到坏帧立即停车”。

## 6. 超时保护

F407 的 `Motor_CAN` 任务每 50 ms 检查一次：

```c
if (last_rx_tick == 0U ||
    (uint32_t)(now - last_rx_tick) > 500U)
{
    target = 0;
    App_Fault_Set(FAULT_CAN_TIMEOUT);
}
```

含义：

- 上电后从未收到合法帧，也会进入超时状态；
- 超过 500 ms 没有合法帧，目标值归零；
- 检测由 50 ms 周期任务完成，所以从“最后一帧”到“目标归零”的实际时间会略大于 500 ms；
- 目标归零后，控制任务在下一个 50 ms 周期调用 `Int_Motor_Stop()`，PWM 归零并清除积分；不是原来的斜坡减速。

## 7. DLC 和测试接口的限制

F103 的测试接口在 `App_MotorCan.c`：

| 接口 | 作用 | 限制 |
|---|---|---|
| `App_MotorCan_SendSpeed(speed)` | 发送合法 SET 帧，DLC=8 | 速度会先被钳制到 `-1000~1000` |
| `App_MotorCan_SendStop()` | 发送合法 STOP 帧，DLC=8 | — |
| `App_MotorCan_SendTestFrame(cmd, speed, dlc)` | 指定命令、速度和 DLC | `dlc > 8` 会被钳制到 8 |
| `App_MotorCan_SendRawFrame(data, dlc)` | 直接指定 8 字节内容和 DLC | 只接受 `1~8`；`dlc==0` 返回 `HAL_ERROR` |

因此：

- 测试帧长错误时，使用 `DLC=7` 或 `1~7` 更可靠；
- 不能用 `DLC>8` 构造“超长帧”，因为经典 CAN 只有 0~8，而且 F103 会把大于 8 的值钳制到 8；
- 测试速度越界时，不能直接用 `SendSpeed(1001)`（会被钳制），应使用 `SendRawFrame()` 手工写入 `0x03E9`（+1001）或 `0xFC17`（-1001）。

## 8. 旧协议和当前控制链的区别

F407 的 `App_can_protocol.c` 还保留了一套小协议：

| ID | 用途 | DLC |
|---|---|---|
| `0x100` | 心跳 | 2 |
| `0x101` | 传感器数据 | 8 |
| `0x200` | 控制命令 | 4 |
| `0x201` | 状态回报 | 4 |

这套协议使用小端字节序，解析结果写入 `g_can_protocol_monitor`，**当前不驱动电机**。`0x301` 由 `App_MotorCan.c` 单独处理，二者不要混淆。

F103 的 `App_can.c` 还定义了 `0x123/0x124` 和校验和，但当前 `CAN_Motor_Test_Task` 没有调用 `APP_CAN_Process()`，所以它属于保留的旧代码，不是当前控制链的一部分。

## 9. 当前发送节奏

- F103 每 50 ms 发送一帧 `0x301`；当前测试任务按 `+100 → +200 → +100 → STOP` 循环，每档约 40 s。
- F407 `Motor_CAN` 每 50 ms 更新一次目标 RPM、编码器反馈、PI 输出和 PWM。
- 500 ms 超时阈值是 10 个发送周期，能容忍偶发丢帧，但连续丢帧超过阈值就会归零。
