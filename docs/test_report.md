### 3.4 已观察到的故障位叠加

Day 13 的实际现象是：帧长错误测试时，`g_fault_flags` 在 `0x02` 和 `0x03` 之间变化。

原因：

- `FAULT_CAN_BAD_FRAME = 0x02` 由非法帧置位；
- 测试期间没有合法帧，500 ms 后 `FAULT_CAN_TIMEOUT = 0x01` 也会置位；
- 两个位叠加得到 `0x03`。

这不是校验逻辑错误，而是故障位按位叠加的正常结果。测试时应检查目标位是否存在，或在非法帧之间周期性插入合法 STOP 帧。

## 5. 异常处理结果

### 5.1 故障位在 `0x02` 和 `0x03` 之间跳动

| 项目 | 内容 |
|---|---|
| 现象 | 注入帧长错误后，`g_fault_flags` 不是稳定的单一值 |
| 原因 | 非法帧置位 `BAD_FRAME=0x02`；没有合法帧导致 500 ms 后叠加 `TIMEOUT=0x01` |
| 处理 | 判定时检查对应位是否存在；需要稳定观察时，周期性插入合法 STOP 清除超时 |
| 结果 | 已解释并保留为测试注意事项 |

### 5.2 STBY 由 PB14 控制时电机不转

| 项目 | 内容 |
|---|---|
| 现象 | PB14 控制 STBY 时电机不转；STBY 直接接 3.3 V 后电机可转 |
| 原因 | Keil 链接阶段报 `L6449E: I/O error writing file 'xxx.o'`，输出 `Target not created`，烧录的仍是旧固件 |
| 处理 | 重新构建，确认 0 error、无 `Target not created`，再重新下载 |
| 结果 | 重新下载后 PB14 控制恢复正常；这是“代码已改但固件未更新”的典型案例 |

### 5.3 Keil `uv4.log` 被占用

| 项目 | 内容 |
|---|---|
| 现象 | 构建提示 `uv4.log` 正被另一进程使用，构建任务退出码 1 |
| 原因 | 残留 `UV4.exe` 进程和 `uv4.log.lock` 占用日志 |
| 处理 | 结束残留 `UV4.exe`，删除 `.vscode/uv4.log` 和 `uv4.log.lock` 后重新构建 |
| 结果 | 构建恢复 |

### 5.4 代码整理中发现的两个问题

| 问题 | 处理 | 验证 |
|---|---|---|
| `App_MotorCan_OnRx()` 和 `Int_can.c` 都对 `0x301` 帧累加 `g_can_rx_count`，导致计数偏大 | 去掉 `App_MotorCan_OnRx()` 中的重复自增，统一由 `Int_can.c` 统计所有接收帧 | F407 全量重建 0 error / 0 warning |

## 6. 结论

### 已经能够确认

- 两个工程都能用当前代码全量构建通过；F407 无警告，F103 只剩 FreeRTOS 第三方头文件的换行警告。
- TB6612 的 PWM 调速、停止、反转在 Day 9 记录中已经实际验证。
- `0x301` 的 DLC 错误能触发 `FAULT_CAN_BAD_FRAME`；测试期间还观察到了 `TIMEOUT` 叠加。
- 故障位按位叠加的设计和 PRIMASK 临界区保护已经落到代码中。

### 不能据此宣称

- 不能宣称“全部故障矩阵测试通过”：帧头、命令的具体实测值没有归档，速度越界未测。
- 不能宣称“500 ms 内电机完全停止”：500 ms 只是目标归零阈值，之后还有斜坡和机械惯性。
- 不能宣称“闭环调速”或“精确 RPM 控制”：当前没有编码器反馈和 PID。
- 不能宣称“已完成硬件急停”：`Int_Motor_Stop()` 是 PWM 归零 + 方向脚拉低，不是独立的安全回路。
- 不能给出收发器型号、终端电阻实测值或总线误码率：这些数据没有留存。
