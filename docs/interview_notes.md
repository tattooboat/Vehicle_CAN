# 面试技术说明

## 一句话概括

用 STM32F103 和 STM32F407 组成 CAN 双节点：F103 发送 `0x301` 测试序列和故障注入帧，F407 在 FreeRTOS 中用 TIM8 编码器反馈做 PI 转速闭环，并实现 500 ms 超时停止和故障位管理。

## 可以写进简历的三点

- 基于 STM32F103/F407 和 CAN 2.0A 搭建双节点电机控制链路，定义 `0x301` 应用层帧，完成帧长、帧头、命令、速度范围的分级校验。
- 在 F407 上使用 TIM8 正交编码器测速和 PI 速度环，将 CAN 指令映射为目标 RPM，通过 TB6612 的 1 kHz PWM 实现闭环调速、换向和停止。
- 通过 F103 注入非法帧，观察故障位叠加并修正测试判定方法；定位过一次“代码已改但 Keil 链接失败、烧录仍是旧固件”的 STBY 假故障。

## 7 个常见问题

### 1. 为什么使用两块 STM32，而不是一块 MCU 控制全部功能？

这个项目里，两块 MCU 的主要价值是**角色隔离和故障注入**，不是一块 F407 性能不够。

- F103 只做命令发送端，代码简单，断电/重启就能模拟 CAN 发送端失联；
- F407 只做实时控制，接收、校验、编码器测速、PI、超时保护和传感器任务都在本地完成；
- 发送端和控制器解耦后，可以单独测试“总线断了会怎样”，不会把测试逻辑混进电机控制任务；
- 两块 MCU 也把 CAN 的分布式通信链路真正跑起来了，而不是在同一块板子上回环。

如果面试官追问“一块 MCU 行不行”，可以直说：**一块 MCU 也能完成这个规模的功能；选双 MCU 是为了演示分布式节点、故障隔离和故障注入，而不是声称单 MCU 做不到。**

### 2. CAN 标准帧 ID、DLC 和应用层协议分别是什么？

要区分三层：

- **帧层**：经典 CAN 2.0A 标准数据帧，11 位 ID，DLC 表示数据字节数，范围 0~8。
- **ID**：电机控制帧使用 `0x301`。
- **应用层**：合法帧要求 `DLC=8`，字段为：

| 字节 | 含义 |
|---|---|
| `Data[0]` | 帧标记 `0xA5` |
| `Data[1]` | `0x01` SET / `0x02` STOP |
| `Data[2..3]` | 有符号 16 位速度，大端，范围 `-1000~1000` |
| `Data[4]` | F103 发送序号，F407 当前不使用 |
| `Data[5..7]` | 保留，F103 填 0 |

速度不是 RPM，而是指令值。F407 按 `target_rpm = can_speed / 1000 × 169` 把它映射为目标转速，再由 PI 产生 PWM；例如 `+100` 对应 16.9 RPM。两节点都配置为 250 kbit/s。

### 3. 为什么用 PI 闭环，而不是直接把 0 跳到 600 的 PWM？

需要先纠正一个前提：**当前 PI 版本已经去掉了原来的 50/50 ms PWM 斜坡**。控制链路是：

```c
target_rpm = can_speed / 1000.0f * 169.0f;
error = target_rpm - actual_rpm;
output = Kp * error + Ki * integral;
```

`can_speed=600` 对应目标约 101.4 RPM，不是 600 RPM。目标从 0 跳到 600 指令时，误差很大，P 项和积分项会推动 PWM，但输出还受积分限幅和 PWM 限幅约束，不会像开环一样直接写一个不受反馈约束的 CCR。

为什么不在 PWM 层直接硬跳：

- 闭环仍然要限制输出和积分，避免饱和后长时间退不出来；
- 目标阶跃本身仍可能带来冲击和超调，当前只做了积分限幅/输出限幅，**没有目标 RPM 斜坡**；
- 如果把“渐变”作为需求，正确做法是给 `target_rpm` 加 setpoint ramp，而不是在 PWM 输出上再叠一层斜坡。

面试时可以这样区分：旧版本是开环 PWM 斜坡；当前版本是“目标 RPM 阶跃 + PI 输出”，两者不要混着讲。

### 4. 为什么 CAN 超时后要把目标速度归零？

因为“最后一帧”不能代表发送端仍然正常。如果 F103 断电、CAN 线断开或总线持续错误，F407 继续执行上一条速度指令就可能导致电机失控。

当前策略：

- 超过 500 ms 没有合法 `0x301` 帧，目标 RPM 归零；
- 置位 `FAULT_CAN_TIMEOUT=0x01`；
- 下一个 50 ms 控制周期调用 `Int_Motor_Stop()`，PWM 归零并清除积分。

500 ms 是一个折中：能容忍偶发丢帧，又能在发送端失效后较快停止输出。它不是安全认证意义上的硬件急停；软件停止延迟约一个控制周期，电机机械停止时间还取决于负载和惯性。

### 5. FreeRTOS 任务与 CAN 中断之间如何传递控制数据？

当前没有用队列或信号量传 CAN 控制数据，而是用两个 `volatile` 共享变量：

```c
static volatile int16_t target_speed = 0;
static volatile uint32_t last_rx_tick = 0;
```

路径是：

```text
CAN RX0 中断
  → App_MotorCan_OnRx()
  → 写 target_speed / last_rx_tick / 故障位
  → Motor_CAN 任务每 50 ms 读一次
  → target_rpm 映射 → 读编码器 actual_rpm → PI → Int_Motor_SetSpeed()
```

这样做的原因是数据量很小、只有一个写者（中断）和一个读者（任务），比队列更直接。`int16_t` 和 `uint32_t` 在 Cortex-M 上对齐访问是原子的。故障位是读改写，已经用 PRIMASK 临界区保护，避免任务清位时覆盖中断刚置上的另一位。

如果状态更多、需要保证“目标值+时间戳+序号”作为一组原子更新，应该改成消息队列或带序号的结构，而不是继续堆 `volatile` 变量。

### 6. 如果收到非法帧，如何避免更新电机目标速度？

在 `App_MotorCan_OnRx()` 里按顺序校验，任一失败立即 `return`：

1. ID 必须是 `0x301`；
2. `len == 8`；
3. `Data[0] == 0xA5`；
4. `Data[1]` 只能是 `0x01` 或 `0x02`；
5. SET 帧的速度必须在 `-1000~1000`。

失败时只做两件事：

- 累加 `g_can_invalid_count`；
- 置位对应的 `BAD_FRAME`、`BAD_COMMAND` 或 `BAD_SPEED`。

它**不会**写 `target_speed`，也**不会**更新 `last_rx_tick`。因此目标速度保持上一条合法值，直到后续合法帧到来；如果一直没有合法帧，500 ms 超时后再归零。

这里有一个容易说错的点：**非法帧不会立即停车**，它只是不能改写目标；真正让目标归零的是后续的超时保护。

### 7. 如果电机没有停止，你会如何定位是 CAN、任务、PWM 还是驱动硬件的问题？

按链路分层排查，不要一上来就换硬件：

1. **先看软件状态**：F407 串口有 `TgtRPM=... ActRPM=... Err=... I=... PWM=...`。如果目标为 0 但 PWM 不为 0，问题在任务/停止分支；如果目标不为 0 但 `ActRPM` 始终为 0，优先检查编码器或转速换算；如果目标不更新，检查 CAN/中断。
2. **看故障和计数**：调试器观察 `g_fault_flags`、`g_can_rx_count`、`g_can_invalid_count`。有 `BAD_FRAME/BAD_COMMAND` 说明帧校验在拦截；有 `TIMEOUT` 说明没有合法帧。
3. **看任务**：用 RTOS-aware 调试确认 `Motor_CAN` 是否还在运行、是否卡在某个 HAL 调用、栈是否溢出。
4. **看编码器**：确认 TIM8 编码器模式已启动，PC6/PC7 有 A/B 相脉冲，正反转时计数差符号正确；如果方向反了，检查 `Int_Encoder_GetOutputRPM()` 的符号修正和接线。
5. **看 PWM**：示波器/逻辑分析仪测 `PB0` 是否有 1 kHz 波形，`CCR` 是否随 PI 输出变化；确认 `HAL_TIM_PWM_Start()` 返回 `HAL_OK`。
6. **看驱动输入**：测 `PB12/PB13` 方向电平、`PB14/STBY` 是否为高；如果 STBY 为低，TB6612 处于待机，PWM 再正常也不会转。
7. **看功率侧**：测 TB6612 的 `VCC`、`VM`、`GND`，确认电机电源和 MCU 共地，`AO1/AO2` 有输出；必要时用替换法换 TB6612 或电机。
8. **最后才怀疑硬件**：先排除“代码没编译进去/没下载成功”这类假故障。Day 9 就遇到过：代码改了 PB14，但 Keil 链接失败，烧录的仍是旧固件，看起来像 STBY 硬件问题。

补充：`ActRPM` 是编码器换算出来的估计值，44 计数/电机转和减速比 35.5 还没用外部测速仪校准；不要把 `ActRPM` 当成绝对精度已经验证的 RPM。当前也没有编码器失效故障位，若目标非零但 `ActRPM` 长期为 0，必须先停机排查，不能让 PI 继续把 PWM 推到限幅。

## 面试时不要夸大的点

- 可以说“当前有编码器反馈的单速度环 PI”，但不要说“PID 已经完全调好”或“全工况稳定”。
- 不要说“500 ms 内电机完全停止”：500 ms 是目标归零阈值；软件在下一个控制周期停 PWM，机械停止时间未测。
- 不要说“所有故障测试都通过”：帧长错误有实测，帧头/命令结果未归档，速度越界未测。
- 不要说“有硬件急停”：`Int_Motor_Stop()` 只是 PWM 归零和方向脚拉低。
- 不要说“绝对 RPM 已经校准”：编码器计数和减速比仍是标定假设。
- 不要把 `App_SpeedPID.c` 说成当前生效实现：`Motor_CAN` 当前用的是 `freertos.c` 内联 PI。
- 不要编 CAN 收发器型号、终端电阻实测值或总线误码率：原记录没有这些数据。
- 不要把 F103 说成“可调速度上位机”：当前是 `100/200/100/STOP` 自动测试序列。
